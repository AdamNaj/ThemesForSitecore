# Themes for Sitecore

An MV3 browser extension (Chrome, Edge, Firefox) that reskins the Sitecore 10.0 to 10.5 back office:
the classic shell (Desktop, Content Editor, Sheer UI dialogs), SPEAK apps and Launchpad, the
Experience Editor's chrome, the login pages and `/sitecore/admin`. Product notes and design principles live in
`PRODUCT.md`; how to write a theme in `extension/themes/README.md`.

## How it works

| Path | Role |
|---|---|
| `extension/background.js` | Registers the content scripts for granted origins, resolves each frame's theme, injects and removes the theme CSS with `scripting.insertCSS`/`removeCSS`. |
| `extension/lib/engine.js` | The page engine, shared with the Sitecore module: runs in every frame, tags `<html>` with `data-sct-surface`, `-theme`, `-version`, `-tokens`, asks its host for the theme, runs the theme's DOM module, holds the first paint until the CSS lands. Everything platform-specific goes through the host (its header lists the interface). |
| `extension/content.js` | The extension's host for the engine: extension storage, the background's CSS swap, the dev hooks. |
| `extension/popup/picker.js` | The popup's preview, hue and strip of miniatures, shared with the Sitecore module's panel; `popup.js` keeps the extension's storage, tab title, tint, import and permissions. |
| `extension/lib/files.js` | A theme's CSS files per surface, in cascade order; shared by `background.js` and the Sitecore module. |
| `extension/lib/detect.js` | URL and markup to surface (`shell`, `speak`, `launchpad`, `login`, `ee`, `admin`, or none). |
| `extension/lib/settings.js` | Each origin's theme (`overrides`; none means Native), filtered by Sitecore version. |
| `extension/lib/color-map.js`, `live-map.js` | The colour-to-token mapping, shared by the build tool and a runtime pass that maps stylesheets and inline styles the build never saw. |
| `extension/surfaces/<area>.gen.css` | Generated by `tools/gen-area-map.mjs` from the stock stylesheets on the local installs. Never hand-edit. |
| `extension/surfaces/<area>.css` | Hand-tuned rules that win over the generated map. |
| `extension/surfaces/bar.css` | Loaded under every theme on every surface: the default badge for the site's postfix in Sitecore's top bar (`<sct-bar-postfix>`, added by `engine.js`), the Sitecore Extensions add-on's database name moved beside Log out, and its field-search clear button drawn as a vector X; white (`OfficeWhite`) and black icons outlined so they show on any panel; taskbar titles that end in an ellipsis on a button that cannot grow; and Sitecore 10.5's extra Content Editor spacing taken out, so a theme looks the same on 10.4 and 10.5. A theme restyles the badge in its own `bar.css`; fixes for add-ons, and for version differences, that every theme needs go here. |
| `extension/themes/<id>/` | One theme, self-contained: `theme.json` (name, group, versions, miniature), `tokens.css` (token themes), `<area>.css`, `bar.css`, optional `dom.js`, `glyphs/`, `preview*.jpg`. Adding a theme touches nothing outside its folder. See `extension/themes/README.md`. |
| `extension/themes/themes.js` | The theme registry, generated by `tools/themes.mjs` from the folders (`npm run themes`); `usesTokens`, `hasDom`, `areas`, `bar` and `previews` come from each folder's files. Never hand-edit. |
| `tools/` | Build (`build.mjs`), generators (`gen-area-map.mjs`, `build-*-css.*`), helpers. |
| `test/unit/` | `node --test` suites. |
| `sitecore/` | The Sitecore-deployed version (see its `README.md`): `host.js` (the engine's host there), the `httpRequestBegin` processor that writes the loader into pages, its config patch. Nothing in `extension/` may depend on it. |
| `test/e2e/` | Playwright: fixture tests, plus `sitecore.spec.js` against the live installs. |

Token themes get `surfaces/<area>.gen.css`, `surfaces/<area>.css` and their `tokens.css` on every surface.
The background fetches every listed file; one missing file makes the whole theme fail silently for that
frame. A new surface therefore needs both `surfaces/<area>.gen.css` and `surfaces/<area>.css`.

## Commands

- `npm test` - unit tests. Run after every change. Fails while `themes.js` or the README's theme table is stale.
- `npm run themes` - regenerate `extension/themes/themes.js` and the README's theme table from the theme folders.
- `npm run lint` - builds the packages, then `web-ext lint` (Firefox's rules) on the Firefox one, the only package
  whose manifest carries `background.scripts`; the warnings it shows today are known.
- `npx playwright test` - e2e. The Sitecore suite needs the `.auth/profile` sign-in (`node test/e2e/login.mjs`, the user signs in; agents never type Sitecore credentials).
- `node tools/gen-area-map.mjs` - regenerate every `.gen.css` from the local installs. Check `git diff --stat` afterwards: changes outside the area you meant come from the installs, and need a sentence in the commit.
- `npm run build` - release zips in `dist/`; the packaged copies switch the dev hooks off.
- `npm run build:sitecore` - the Sitecore-deployed version in `dist-sitecore/files/`, one webroot overlay for 10.4 and 10.5 (the DLL is compiled once against 10.4's `Sitecore.Kernel`; Sitecore's assemblies are not strong-named).
- `npm run package:sitecore` - the same, packaged: a Sitecore package (`.zip`, for the Installation Wizard) and a Web Deploy package (`.scwdp.zip`), versioned from `package.json`; the second needs `msdeploy.exe`.

## Environments

The local Sitecore installs live in `sitecore.local.json` (gitignored; copy `sitecore.example.json`). Notes about
the machine itself (which browsers run the extension, other extensions, how the user connects) go in
`AGENTS.local.md`, also gitignored, which `CLAUDE.md` imports. Read it when it exists.

- `hosts`: the 10.5 and 10.4 CM sites the e2e suite and the verify scripts open, signed in once through
  `node test/e2e/login.mjs`. A customised install is worth having here: project CSS and a strict CSP (one that
  blocks `data:` images) catch bugs a stock install hides. `identityHosts`: their identity servers.
- `webroots` `10.5` and `10.4`: **stock** installs. The generators read their stylesheets, so a customised
  one would put its project CSS into every theme. `identity`: the identity servers' webroots.
- `webroots.legacy`: Sitecore 10.0 to 10.3 UI files (no database needed), unpacked from the installers.
  `detect.js` gives these versions 10.4's themes; `gen-area-map.mjs` maps their stylesheets.
- `webroots.sitecore6`: Sitecore 6.6 files, the style reference for the Copenhagen theme.
- The extension runs unpacked from `extension/`. Each browser keeps its **own** theme settings.

## Verifying a change

Use the `sct-verify` skill (`.claude/skills/sct-verify/SKILL.md`) before saying a change works. In short:

- **The user's real browser is the test that counts.** Playwright's Chromium has none of the user's other
  extensions (the Sitecore Extensions add-on, Dark Reader) and different timing. Two regressions on 2026-10-21 passed Playwright and broke
  in the user's Chrome.
- **Open the URLs people actually use**, not tidied ones: `/sitecore/shell` (no trailing slash), Launchpad
  through `/sitecore/shell/sitecore/client/...`, the Experience Editor via `?sc_mode=edit`.
- **Check every frame**, not just the top document: the Experience Editor ribbon, Content Editor frames and
  dialogs are separate documents with their own `data-sct-*` attributes.
- **Read the screenshots** you take. Say what you verified, where, and what you could not.

## Adding or reworking a theme

Use the `sct-new-theme` skill (`.claude/skills/sct-new-theme/SKILL.md`). Its `pitfalls.md` holds every
correction reviews have had to make across the existing themes; read it before writing theme CSS.

## Before blaming the code

When the user reports something broken, rule these out first:

1. **The browser's own theme setting** for that host. Chrome and Edge keep separate settings; Native means "do nothing".
2. **Other extensions that restyle pages** (Dark Reader, Stylus; `AGENTS.local.md` says which the user has). Dark Reader makes light themes look dark.
3. **A stale dev install.** An unpacked extension re-reads CSS from disk on every injection but keeps running old content scripts until it is reloaded. Removing a theme needs the exact CSS text that was inserted, so after a CSS file changes on disk, a live theme switch in an already-open tab leaves the old theme's CSS behind. Reload the extension, then the tabs.
4. **The Sitecore session.** A hung SPE script blocks every request from that sign-in (see below).

## Gotchas

- **Never touch a child frame's `contentDocument` from a parent content script before that frame's `load` event.** It stopped Chrome from theming the Experience Editor ribbon.
- **Sitecore serves pages at bare folder URLs** (`/sitecore/shell`). `detect.js` appends a slash before matching prefixes; keep it that way.
- **SPE dialogs in tests:** always press Cancel before a script ends. A Read-Variable or Show-Result window left open, then aborted, hangs that sign-in's ASP.NET session until the request times out (up to 10 minutes).
- **Every Playwright launch starts a new Sitecore session.** A few dozen launches against one install use up its
  license's concurrent users ("The maximum number of allowed users has been reached", `LicenseOptions/StartPage`)
  until the sessions time out. Visit many pages and themes from one browser instead of one launch each.
- **`.auth/profile` is shared** by every session's Playwright runs. Never kill a Chrome running on it. For ad-hoc runs, copy it to your scratchpad (skip the caches and `Singleton*` files); copies' sign-ins expire after about an hour, so re-copy rather than asking the user to sign in.
- **Driving the user's Chrome:** reload the extension by posting `{type: "sct-dev-reload"}` from a Sitecore page, then reload the page. `{type: "sct-dev-set", values: {...}}` replaces the whole overrides map, so restore the user's choices afterwards.
- **Edge cannot be driven** by Claude in Chrome. Its state can be read from its profile folder (`Secure Preferences` and the extensions' settings folders); ask the user to reload it.
- **Playwright's headless Chromium hides scrollbars** (`--hide-scrollbars`); launch with `ignoreDefaultArgs: ["--hide-scrollbars"]` to check themed scrollbars.
- **Git Bash heredocs halve doubled backslashes.** Write scripts containing regexes with the file-writing tool, not `cat <<EOF`.
- **Code shared with the Sitecore module lives in `extension/`**, because an unpacked extension cannot load files from outside its folder. Shared files must not touch extension APIs, nor use `Array.from` (Sitecore's Prototype.js replaces it); those belong in `content.js`, `background.js` or `popup/`, and Sitecore-only code in `sitecore/`.
- **An install with the Sitecore module deployed** (`npm run build:sitecore`, copied over the webroot) gets the module's loader and theme picker on its pages; with the extension enabled for the site, the module stays out of the way.
- **Copenhagen's `shell.css` is mostly generated** by `node tools/build-sitecore6-css.mjs` between BEGIN/END markers; hand-written rules go after END and carry `:not(#sct-sc6)`.
- **Never copy Sitecore's (or anyone's) image files, logos or embedded images into the extension.** Draw our own: the Sitecore 10.4 and 10.5 themes' glyphs come from `node tools/build-sitecore-glyphs.mjs`, which `tools/css-diff.mjs` points its output at by name.

## Working in this repo

- **Side sessions in worktrees** commit to their own branches. Their work is not in the main checkout, so it is not in the user's browsers, until it is merged. Merge only when the user says so. A worktree has no `node_modules`, `sitecore.local.json` or `.auth/profile`: run `npm ci`, copy `sitecore.local.json`, and set `SCT_PROFILE` to the main checkout's `.auth/profile`.
- **No em-dashes or en-dashes** in any file you write; use a hyphen.
- **Commits:** a descriptive subject plus a bullet body; one feature or theme per commit.
